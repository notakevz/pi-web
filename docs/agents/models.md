# Models and provider auth

## Model defaults for new sessions
`GET /api/models` returns `defaultModel` from `~/.pi/agent/settings.json`; `ChatWindow` pre-selects it for new sessions. Browser model/thinking picks are applied atomically while the AgentSession is built and are **session-scoped**: neither startup nor a mid-session `set_model` / `set_thinking_level` writes `settings.json`, as pi's `/model` and `/thinking` persist only on Ctrl+S (otherwise a one-off pick becomes the TUI's default too).

The two existing stars have different scopes. The **model star** saves `defaultProvider`/`defaultModel` for new chats. The **reasoning star** saves the current exact `provider/modelId` entry of SDK-native `modelThinkingLevels` via `PUT /api/models/default { modelThinkingLevel: { provider, modelId, level } }`. It never changes the default model or the ordinary global `defaultThinkingLevel`. Both also select the saved value for the current chat. Ordinary model, effort and on/off picks remain session-scoped; only an explicit star writes shared defaults (which terminal Pi also reads). Model IDs are not guessed or hard-coded: the same ID at different providers has separate defaults.

`GET /api/models` returns the effective merged `modelThinkingDefaults` map, `fallbackThinkingLevel` (the ordinary fallback including project overrides), and the resolved default model's `defaultThinkingLevel`. The raw global `savedDefaultThinkingLevel` stays available for older clients; it is not the new reasoning-star marker. The hook passes the displayed model's exact saved entry to ChatInput, so the star follows model switches and a fallback is not falsely shown as saved. New drafts resolve `enabledModels :level` pin → exact per-model default → effective global fallback → pi's concrete medium fallback, clamped to supported levels like pi-ai. Switching models clears the prior model's temporary effort and applies the target's resolved default, even if a dormant/live SDK wrapper still holds settings from before a star save. First send must not repeat `set_model` on an already initialized draft: that would reapply stale SDK settings. Model switches during creation finish before the prompt, and creation replies only adopt thinking when both captured model and effort overrides are still current.

Existing-session switches publish the target model and its resolved effort together, before either RPC replies; do not clear the effort and briefly show the previous model's value or a medium fallback. Keep both overrides through canonical reload, checking the pending ref synchronously before queueing React state updates (a functional updater must not read a mutable pending ref later). A newer explicit effort stays visible until its own RPC completes. Canonical success/failure reads use client-only `fresh` to bypass any pre-switch single flight, without sending `force=1`; latest-applied read IDs reject older history/state replies after a newer view succeeds. A separate confirmed-write floor invalidates reads started before an acknowledged model/effort write, even if canonical validation later fails; this does not change the ordinary failed-newer-read fallback for reads not invalidated by a mutation. Failed switches discard the optimistic effort and reconcile the actual model/level. `hooks/model-thinking-defaults.test.mjs` gates model, effort, history and failure responses; `hooks/model-switch-render-batching.test.mjs` uses actual source statements and real React server render-phase queues, including a negative control for the old ref-updater bug. This is not full browser acceptance.

The save route accepts only a visible model and SDK-supported effort. It returns `409 { reason: "project-scope", settingsPath }` only for project keys that actually shadow the edit: a matching per-model entry blocks that model's star, not another model's entry or a project-wide thinking fallback. A conflicting scope `:level` pin gives `409 { reason: "thinking-level-pin" }`; unsupported efforts are rejected rather than saved and silently clamped. Web per-model writes are serialized and reload settings before the native setter (which marks the whole map); another process using the SDK can still race that reload/write boundary. Existing global-thinking PUT requests remain compatible. Both selectors use `SelectorRow`; `ModelSelector` shows stars only when given `onSetDefault`, which the subagent profile form does not pass.

The reasoning control stays usable while a run streams: pi-agent-core snapshots `reasoning` when a run starts, but `AgentSession`'s `prepareRequest` / `prepareNextTurnWithContext` re-read `agent.state.thinkingLevel` before every model request, so `set_thinking_level` applies from the next request (the response already streaming keeps its level). `lib/thinking-level-mid-run.integration.test.mjs` pins this; if an SDK upgrade breaks it, disable the control while streaming rather than let it change nothing.

## Unified reasoning menu
`GET /api/models` includes `modelList[].thinkingToggle`, derived by `hasThinkingToggle()` (`lib/thinking-controls.ts`) from the actual OpenAI-completions compatibility settings, not model IDs or the number of configured levels. Qwen/qwen-chat-template have an explicit boolean; generic chat-template requires `enable_thinking: { $var: "thinking.enabled" }` without `omitWhenOff`. The UI also requires SDK-supported `off`; `thinkingLevelMap.off: null` is **unsupported**, and the SDK clamps off back to an enabled level. Never compensate by merely inserting off into a browser menu.

These transports use **one dropdown**, never an independent bulb toggle or a separate toolbar star. Multiple enabled levels (Qwen3.8) render contiguous `Reasoning off / low / medium / xhigh` rows, **without a separator**. The trigger shows `Reasoning off` or `Reasoning · <effort>`; off is the active row when disabled, and selecting an effort enables that level. Models with multiple enabled efforts render the off row in the same value/description/star columns as efforts: `off | Reasoning off | star` (description translated). A single enabled marker (Gemma) instead renders symmetric, label-only `Reasoning on / Reasoning off` rows with no separate off value/description columns, never its internal medium or transport none value. Both rows retain the same checkmark and star gutters. This is display-only; trigger labels, native off and star handlers are unchanged. Non-toggle/GPT menus retain their supported labels and values. No visible auto value is introduced.

**Every supported menu option can be starred**, including Qwen off and both Gemma on/off. Saving on for a binary model stores its real enabled SDK marker (Gemma medium); saving off stores native off, not the transport marker `none`. All default stars live inside the menu; the trigger has none. A saved row uses SelectorRow's dim static star; other rows offer the save action. Opening the menu changes nothing; ordinary row selection only affects this conversation, and a star selects and saves this exact provider/model default. Off has no special new-chat exception: new conversations and model switches use the same native per-model default resolution as effort levels. There is **no forced new-chat on policy, per-model conversation-memory layer, extra transcript metadata or browser storage**. This explicitly supersedes the proposed independent-toggle/default-on design. Existing sessions retain their SDK thinking state; this change does not rewrite them or their shared settings.

Controls remain available mid-run under the next-request rule above; they do not interrupt the request already streaming. `components/ChatInput.reasoning-menu.test.mjs` executes the actual TSX control, menu rows and star handlers, including saved off, binary on's internal marker, no separator and no duplicate toolbar action. `components/ChatInput.thinking.test.mjs` covers the full SSR trigger. Backend default and wire tests continue to pin the existing persistence/transport behavior.

A compatible model configuration uses `off: "none"` as the SDK support marker for both model families. For Qwen, `thinkingFormat: "qwen"` with `supportsReasoningEffort: true` emits top-level `enable_thinking` plus low/medium/xhigh when enabled, and `enable_thinking: false` **without** effort when off. Gemma's chat-template binding emits `chat_template_kwargs.enable_thinking` only. Do not send the internal off marker as an effort or collapse Qwen to a fake single medium level. Qwen3.8's [official template](https://huggingface.co/Qwen/Qwen3.8-27B/blob/main/chat_template.jinja) really supports those three efforts and skips their instructions when thinking is disabled; this differs from original Qwen3. Current [oMLX request models](https://github.com/jundot/omlx/blob/main/omlx/api/openai_models.py) support both top-level boolean and effort, but the deployed server version must be checked separately. The SDK wire contract is pinned by `lib/thinking-requests.test.mjs` against a loopback mock, not a real model.

## Model selector and the mobile keyboard
The keyboard-open CSS keeps the composer's controls row while its model picker is open, so the panel and its focused filter stay (#1271). While open, `ModelSelector` re-reads its trigger's rectangle on viewport resize/scroll and on the root's `style` / `data-keyboard-open` writes (`useViewportHeight` settles WebKit/IME heights with no viewport event), since the shrinking app moves the trigger. Fixed coordinates are the layout viewport's, which the keyboard does not shrink: an upward panel hangs from `top` with `translateY(-100%)`, never a `bottom` derived from `visualViewport.height`, space is measured from `visualViewport.offsetTop`, and an upward panel ends above the keyboard even when its trigger is under it (a Settings field). The re-read always sets a new rectangle: the panel also reads the visual viewport, which can change while the trigger stays put. `e2e/model-selector.mjs` simulates the keyboard; native keyboards remain a real-device check.

## Remote provider catalogs
Built-in model lists are frozen at the pinned SDK version; newer models come from the SDK's pi.dev catalog overlay, which `ModelRuntime.refresh()` persists to `~/.pi/agent/models-store.json` (the pi CLI fills it too) and which restores offline. pi-web's own runtimes only restore it (`allowNetwork: false` / `refreshOnCreate: false`, listed in the header of `lib/model-catalog-refresh.ts`). That module's network pass runs **only when the user asks** (the "Refresh catalog" button in `EnabledModelsSection` → `/api/models/refresh`), never on a timer or on another request's path, which must not wait on a slow catalog. It calls `refresh()` with `force: true` and never `allowNetwork`, so pi's `PI_OFFLINE` rule holds (`reason: "offline"`), and `shareModelCatalogRefresh()` joins concurrent presses for the same providers. The route returns no model list: a change runs `invalidateModelsCache()` and reloads the panel, whose ordinary `/api/models` load builds a fresh runtime and whose `/api/models/enabled` load refreshes the shared one offline (below); both restore the store.

## Providers registered at `session_start`
No model listing starts a session: `/api/models` builds a fresh `ModelRuntime` per load, and the Models panel's routes share one (Auth and model config, below). Some extensions register their provider only in the first runtime of a process and defer later registrations to `session_start` (pi-claude-bridge, so a subagent sharing its parent's registry keeps the parent's stream function). Without help their models showed only on the first listing after startup, vanished on a folder switch, and a session could not start on them. `lib/deferred-provider-models.ts` remembers the available models of every runtime pi-web builds (listings, `createModelRuntimeWithExtensions()` and every call of the shared runtime, sessions once their extensions are bound) and adds back the models of providers a runtime **does not register at all**; a provider it registered but cannot use (signed out) is never added. `startRpcSession()` builds a session whose requested or restored model is such a deferred one on the default model, then switches to it with `set_model` once `session_start` has run; with no usable model requested, likewise for the pick `/api/models` pre-selects (the default when in scope, #1240). After the switch it sets the thinking level pi's `createAgentSession` gives that model at startup (a resumed session's saved level; a new one's requested level, `enabledModels` pin or `modelThinkingLevels` entry; then `defaultThinkingLevel`, else `medium`): `set_model` alone falls back to the stand-in model's level. A project-only extension that defers its provider would also appear in other folders' listings; picking it there leaves the session on its default model.

`lib/rpc-manager-deferred-model.integration.test.mjs` also pins the interaction with per-model reasoning stars: a deferred model's saved level (including off) beats the global fallback and a non-thinking stand-in, an enabledModels pin beats that saved default, and an explicit request beats both. Reopening an existing conversation retains its historical effort even if a star was changed afterward. These are isolated SDK/session fixtures, not real-provider requests.

## `enabledModels` scoping
`enabledModels` uses pi's `--models` syntax: minimatch globs against `provider/modelId` or a bare `modelId`, fuzzy matching for non-glob patterns, an optional `:thinkingLevel` suffix. Never compare patterns as strings: `lib/model-scope.ts` delegates to the SDK's `resolveModelScopeWithDiagnostics()` so pi-web and the TUI agree, and falls back to every available model when the patterns resolve to nothing. `startRpcSession()` resolves the scope before creating an AgentSession and passes the initial model, thinking pin and SDK-native `scopedModels` atomically; `GET /api/models` uses the helper only for selector data, `thinkingLevelPins` and `modelScopeWarnings`.

The selector lists models in pi's `/model` order (`orderSelectorModels()`): a scope in `enabledModels` order, otherwise sorted by provider id only, so a models.json provider keeps its file's order (#783). `ModelSelector` groups by provider in first-appearance order and never re-sorts; never sort by name in the route or the client.

The Models panel edits it only through `/api/models/enabled`, never with patterns composed in the browser. Every toggle is a **minimal edit** (`lib/enabled-models.ts`, ADR 0004): an unmatched pattern stays verbatim, only the pattern covering a switched-off model is expanded in place (keeping its `:level`), and a fully enabled provider with two or more entries collapses into one glob (an enumerated list rots when a catalog renames a model); a lone exact reference stays. Never rewrite the whole list from `getAvailable()` like the TUI's `/scoped-models`: it sees only providers passing `checkAuth()` right now, so it would drop a signed-out provider's entries and flatten globs and pins. **Never assume `provider/*` covers a provider**: minimatch's `*` stops at `/`, missing nested ids (`commandcode/sakana/fugu-ultra`, most OpenRouter ids); `resolveProviderGlobs()` keeps `provider/*` or `provider/**` only when it matches exactly the provider's models, else writes the provider model by model.

- Switching off the last enabled model is refused, `409 { reason: "last-model" }`: an empty scope means every model.
- Writes go to the global settings file only. A project `.pi/settings.json` `enabledModels` replaces the global array, so the route reports `scope: "project"` and the switches are read-only. The route returns the deciding file as `settingsPath`, which the banner names with the count (`~/.pi/agent/settings.json · enabledModels 20/104`).
- Built-in and extension-registered providers get per-model switches; a models.json provider gets one `EnabledModelsProviderSwitch` in its detail header beside Delete (ADR 0004), on only while all its models are on, so a partial selection reads off beside the sidebar's `1/2` and one click completes it. Why a switch cannot move (the last enabled models, a project scope, the provider missing from the runtime) is the note under the detail header (`EnabledModelsProviderSwitchNote`), which the switch points at with `aria-describedby`; a built-in provider's rows and Disable all point at the section's scope and last-model notes likewise. A tooltip alone never shows on a touch screen ([settings-ui.md](settings-ui.md); ADR 0004 records the change).
- A models.json provider missing from the runtime (unsaved edits, no models, a key that does not work) is never reported as a sign-in problem: its switch is disabled with that note, while `EnabledModelsSection` (built-in providers only) keeps the sign-in empty state.
- `op: "prune"` is the only operation that drops unmatched entries (cleanup after a catalog rename); `op: "clear"` removes the setting; every other operation preserves them.
- Saving models.json calls `op: "resync"`, the only operation that repairs entries (a toggle never touches what the user did not switch): it rewrites renamed models, then renamed providers (model references still spell the old provider id), cuts back entries whose provider prefix no longer scopes them, and re-asserts providers fully enabled before the save. Otherwise a rename corrupts the scope: pi also matches the bare `modelId`, so a provider renamed to `stepfun` makes `stepfun/*` enable `commandcode`'s `stepfun/Step-5-Preview`; a model renamed to an id with a slash leaves `provider/*`; a renamed sole entry resolves to nothing, i.e. every model. `ModelsConfig` must mirror every draft array move in `savedModelIdsRef` so `collectModelRenames()` can tell a rename from an add or a delete.

## Context-window overrides
Each model row of a managed provider (`EnabledModelsSection` given `contextSettings`) carries one compact text field, `ModelContextWindow`, editing `providers[provider].modelOverrides[modelId].contextWindow` in the **same models.json draft** as custom models; the shared Save writes it. The row keeps its one-line height: no visible label (an `aria-label` names the model, a `title` says tokens), no Default button, no current-value line; one note above the list says what the fields are; the shared footer says how open sessions apply saved model edits. The placeholder is the window pi resolves for the model (the enabled-models view's `contextWindow`, from the SDK-resolved model, overrides included), so a blank field means no override. It reads the saved file, not the draft: a cleared override still shows its old value until Save. Clearing the field removes only `contextWindow`, pruning empty containers while preserving credentials and other overrides. An overrides-only entry stays under its managed provider rather than appearing again as a custom provider; it is listed as custom only once `/api/auth/providers` has answered without that provider (a failed request counts), so it does not flash there while the lists load. The detail pane opens the custom-provider form only for an entry that list shows, so a first or remembered selection of such an entry stays blank until the lists answer and it moves to its managed provider.

Save (client, then the route) checks every override with `parseContextWindow()`: text typed in the field must be a whole token count, while a number already in the file only has to pass pi's own check (`exclusiveMinimum: 0`, so `400000.5` loads), or one hand-edited value would block every unrelated save. A value pi refuses (`0`, `null`, a non-numeric string) is refused with the model's `provider/id`: pi drops the whole models.json on a schema error. An invalid draft stays visible, marked `aria-invalid`, and the footer names the model.

New runtimes pick up the saved budget; a loaded session picks it up when its model is selected again (below). Pi 1.2's `/reload` reloads resources but retains the session's model metadata, so do not promise that it applies this edit. This changes Pi's context accounting, not the provider's actual limit; `enabledModels` switches still save separately and immediately.

## Applying saved model edits to open sessions
A session binds a model object; saving models.json does not touch it (#1273). As pi's `/model`, which refreshes the runtime before listing, `set_model` refreshes the chosen provider (`allowNetwork: false`, `providers: [provider]`, 15 s) before looking the id up, even for an id it already has, and the live composer's `ModelSelector` sends `set_model` for its already-selected row (`onReselect`). The hook gives this click its own path: an uninitialized fresh draft stays a draft, while an existing wrapper (including a draft initialized by System/Tools) refreshes without any default `set_thinking_level`. Real model changes still apply the target's resolved per-model default above. A failed or timed-out refresh keeps the cached definitions, as the TUI does. An unchanged definition is not bound again (no `model_change` entry, no `model_select`); a same-id edit keeps the session's thinking level, which the SDK clamps to the new capabilities. `/reload` does not rebind the model, matching pi.

Reselect holds the model-switch flight through a client-`fresh` canonical history/state read (never `force=1`), fences pre-write reads with the confirmed-write floor, and adopts the SDK's clamped level, including off. A newer explicit effort waits for the successful flight and keeps its optimistic display through its own write and targeted canonical state read; both the displayed level and an initialized draft's explicit effort then adopt the SDK's actual clamp (including off), not the requested effort. This confirmation checks effort change id, session/mount and settings-read ordering, so it cannot clear a later explicit pick. Failed refresh commands still reconcile actual state and show a notice; their waiting effort writes are cancelled too, so their optimistic levels must be discarded. An automatic initialized draft adopts the native clamp for its wrapper without inventing an explicit effort to carry across folder remounts. `hooks/model-thinking-defaults.test.mjs` covers the hook sequencing (strict HTTP mocks, no provider calls); `lib/rpc-manager-model-config.integration.test.mjs` separately covers saved same-id definitions, SDK clamping and unchanged reselection adding no model/thinking entries.

Status polls omit the full system prompt (`?systemPrompt=0`); reconciliation's one-off finish read and `agent_end` still fetch it. Both full-prompt replies are guarded by captured session, logical prompt-run id and mount generation, so a delayed old finish cannot replace the next run's prompt or a remounted view. Status reconciliation and `agent_end` gate only their model/effort sync on the confirmed-write floor and latest-applied history read, so an older reply cannot undo a confirmed model/effort change (including a clamp confirmed after a lost write acknowledgement). Same-run full prompts and extension state remain eligible after a newer prompt-free history read; usage keeps its independent request ordering. `hooks/context-usage.test.mjs` includes delayed-reply and negative-control coverage. This affects only displayed state, not the SDK prompt or tool policy.

## Auth and model config
- `ModelsConfig` combines `~/.pi/agent/models.json` with provider auth status from pi's `ModelRuntime` (`/api/auth/providers`).
- **One extension-loaded runtime per agent dir** serves `/api/auth/providers`, `/api/models/enabled`, the logout and API-key provider lookups and MCP Test's provider token (`getModelRuntimeWithExtensions()`, `lib/model-runtime.ts`; #1226). Building one runs every extension at cwd = agent dir, and the SDK's extension factory cache holds one cwd, so a build per request re-imported every extension between two of a project's session starts and blocked the event loop meanwhile (two per Settings › Models open, one per switch or auth action). Only the registrations are reused: every call runs `refresh({ allowNetwork: false })` and `rememberProviderModels()`, which read auth.json, models.json and models-store.json again, so auth status is as fresh as a new runtime's. The calls refresh one at a time, each after it was asked (`serializeByKey()`): when two refreshes overlap, the SDK keeps only the later availability pass and the earlier caller returned the status from before both (Settings asks for the lists and the switches at once, so a key just saved read as missing). Each call awaits the build before it joins that queue, and each built runtime has a queue of its own: the SDK awaits extension factories, and extension providers' `refreshModels()` in an offline refresh, with no timeout, so one stuck there would otherwise hold every later call, even after invalidation. A plugin change (every `POST /api/plugins`, also a failed one: an update can fail halfway) and a session's `reload` or an extension's `ctx.reload()` drop the entry (`invalidateModelRuntimeWithExtensions()`), and a failed build is not kept. An in-place plugin update keeps the package's path, so while the SDK's factory cache sits at the agent dir the rebuild reuses the old factory: the update shows after `/reload`, or once a session start in a project has moved that cache, when the entry is next built (at the latest when it expires). The entry also lasts at most 10 minutes from the end of its build, only a backstop for changes made outside Pi Web (`pi install` from a terminal, an edited extension file). A build still evicts a project's cached factories once (upstream earendil-works/pi#10911 was closed). The OAuth login stream and the catalog refresh still build their own (`createModelRuntimeWithExtensions()`): `login()` and a network `refresh()` change the runtime they run on, for seconds.
- Keep an omitted provider `api` unset in the editor and discovery request: pi resolves the protocol for built-in providers. Opening a provider must not persist a guessed protocol. New custom providers still start with an explicit `openai-completions` default.
- Provider listing is capability-driven, never id-driven: `lib/provider-listing.ts` decides membership from `auth.apiKey.login` / `auth.oauth` plus the stored credential type, so a dual-auth provider (anthropic, github-copilot and others; the set changes between SDK releases) appears exactly once. `lib/provider-listing-runtime.ts` adapts `ModelRuntime` to it.
- auth.json holds **one** credential per provider and `ModelRuntime.logout()` deletes whichever it is, so the delete routes use `removeStoredCredentialIfType()`, which compares and deletes under pi's auth-file lock. After any auth change `ModelsConfig` refreshes *both* provider lists, or a dual-auth provider renders twice.
- OAuth/device-code/manual-code flows stream from `GET /api/auth/login/[provider]`; a manual code POSTs back with a short-lived token kept in `globalThis.__piLoginCallbacks`.
- API-key routes store and remove keys through `lib/provider-credential-store.ts` (`storeProviderCredential()` / `removeStoredCredentialIfType()`), not `AuthStorage`, and never through `ModelRuntime.login()`, which runs an unbounded catalog refresh. Status endpoints never return the raw key.
- The model test route is `app/api/models-config/test/route.ts`; `app/api/models/test/` does not exist.
- A custom model's Advanced settings edit native `models[].baseUrl` (pi has no `modelOverrides` equivalent). Blank removes the key, so the model inherits the provider URL again; `api` and `baseUrl` inherit independently. The field only trims whitespace, never adds `/v1`. Catalog matching uses the effective URL. Test sends the whole draft model, so any edit clears its result and a request id drops replies for an older draft.
- A models.json model on `anthropic-messages` (its own `api`, else its provider's) gets **Claude adaptive thinking** under Advanced settings › Compatibility, which writes pi's `compat.forceAdaptiveThinking` (built-in Claude 4.6+ models set it in generated metadata; pi never infers it from a custom model's id). Without it pi sends `thinking.type: "enabled"` with a token budget (`xhigh` and `max` clamp to high's 16384). Claude Opus 5.5 through a gateway answered that with an empty thinking block and no bytes at all until the answer began, so minutes of silent thinking ended in `terminated`; adaptive thinking streams the summary. Switching it off removes the model's key, or writes `false` when the provider's `compat` turns it on.
- Fetch models (`lib/model-discovery.ts`) copies only capability fields whose meaning does not vary between gateways into the added entries: `contextWindow`, `maxTokens`, `reasoning: true`, and a `thinkingLevelMap` from an advertised effort list naming pi's own levels (others `null`, `off` never touched). Ambiguous fields (`max_tokens`, `default_effort`) and junk values are dropped (#856).
