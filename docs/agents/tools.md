# Tool selection and built-in extensions

## New session tool preset
The composer treats its mode as a **local draft**, not a live `set_tools` command: selecting plan/build/full makes no request. An ordinary Send freezes its `toolNames[]` and submits them with the prompt. `sendRpcSessionPrompt()` serializes submission and the wrapper applies a nonempty mode synchronously inside the same prompt admission, before asynchronous preflight; a busy task refuses the whole submission. Steer/follow-up messages omit `toolNames` and inherit the active run. Legacy callers can still use `set_tools`; crossing a Chat-only resource boundary at Send reuses that server-side recreation path, with the recreated session id in the ACK when necessary. Profile-scoped child chats cannot change their resource ceiling through this UI.

Tool names are passed at session creation (`POST /api/agent/new` → `toolNames[]`) and persisted in versioned `pi-web:tool-selection` custom entries (ADR 0002). No entry, or a later `cleared: true` one, means no pin: ordinary sessions now resolve to local **build** (four coding tools), not pi's `defaultTools`. The legacy `configured` wire sentinel still sends no `toolNames`; no new mode entry format is introduced. An empty array is Chat only, resolved before services are created: no extensions/skills/prompts/themes, and the ordered contents of Pi's discovered context files replace Pi's base prompt. Crossing the Chat-only boundary or clearing a pin rebuilds the wrapper; changing between nonempty presets updates it in place.

**Chat only has no extension providers** (#804): the model selector's listing loads extensions, the session does not. A model only an extension provides (one `findDeferredModel()` remembers but the Chat-only runtime lacks) is named as such: a start refuses it when the browser chose it, `set_model` refuses it instead of "Model not found", and a prompt in a session that could start on no model at all names the one it wanted rather than pi's "No API key found". With no pick, another model in scope stands in for an extension's default, as for any default out of scope.

**Exact system prompts go through `before_agent_start`.** Chat-only sessions register `lib/exact-system-prompt.ts` as an inline extension factory, and subagents (any profile in replace mode, or one naming `skills:`) the equivalent handler in `lib/subagent-skills.ts`, which appends the named skills or, in replace mode, pi's skill catalog; the handler returns `{ systemPrompt }`, which the SDK sends as the provider's leading system prompt for the run while the transcript keeps Pi's structured sections. Assigning `agent.state.systemPrompt` (a getter replayed from transcript system messages) throws, and patching `prepareNextTurnWithContext` never reaches the model. `get_state.systemPrompt` reports the exact prompt for those wrappers. Subagents persist their tools and the profile's skill / extension switches in `resourceSnapshot`, and extensions never expose the reserved `Agent`, `get_subagent_result` or `steer_subagent` to them (ADR 0002).

Every genuinely fresh composer starts in **build** (`NEW_SESSION_TOOL_PRESET`, the builtin set `read, bash, edit, write`), including after changing folders/remounting. Changing this chat to plan/full is session-scoped and does not change the next fresh composer. The old browser `pi-tool-preset` value is neither read nor rewritten by useAgentSession; `tool-preset-preference.ts` remains only as a legacy compatibility helper. Keep `DEFAULT_TOOL_PRESET` as build for historical unpinned sessions and direct legacy API requests: changing that constant would silently alter existing chats. Existing pinned sessions restore their own `toolNames` from `GET /api/sessions/[id]`, then live `get_tools`; legacy none stays Chat only.

**Tool exposure.** pi activates `direct` and `model-only` tools on registration unless their definition sets `defaultActive: false` (`codemode` and `tool_search` do), leaves `codemode` and `deferred` tools undeclared until something activates them, and ignores `hidden` (withdrawn) tools in `setActiveToolsByName()`; `get_tools` leaves hidden tools out.
- Pi Web's environment-sanitizing `bash` (`lib/project-command-env.ts`, ADR 0001), an extension tool standing in for pi's built-in, sets `defaultActive: false` too, so like the built-in it is on only when `defaultTools` (pi's default list included), a preset or `set_tools` names it; registered active, it came back in every session whatever `defaultTools` left out (#1235). A user extension's `bash` still replaces it (`preferUserBashExtension()`) and activates as in the CLI.
- `get_tools` reports an active tool's description from `agent.state.tools`, what the model is sent. Under `codemode.mode: "only"`, while `codemode` is active, the active `direct` tools stay active and callable (`get_tools` reports them so, with `declarationHidden: true` from the AgentSession's private `_hiddenDeclarations`), but codemode's `hiddenDeclarations` leave their declarations out of every request, so the model reaches them only from scripts. The toolbar's Tools panel lists only what requests declare; presets still read `active`. A preset still bounds them: a `direct` tool is callable only while active. `prepareLoadout` hooks rewrite it there on every loadout change (tool registration included): codemode's definition holds only the intro, while the declared one lists the tools scripts can call, MCP namespaces and types, and appends the codemode declaration to the callable `direct` tools.
- **Fork modes** (`lib/local-tool-modes.ts`): upstream `read-only` / `default` / `full` wire IDs and persisted builtin lists remain plan / build / full respectively. Plan declares `read, grep, find, ls`; build `read, bash, edit, write` (PowerShell follows the existing shell preference). Both admit only vetted extras, never arbitrary extension/MCP tools: nonhidden `webfetch` with `readOnlyHint: true` and description containing `Read-only webfetch:`, plus either the genuine built-in host controls (`Agent`, `get_subagent_result`, `steer_subagent` identified by SDK source path `<inline:pi-web-subagents>`) or, when that host is absent, nonhidden external `subagent` whose description contains `In plan/build, children cannot load extensions or MCP`. A registered host supersedes and execution-blocks external `subagent` in every mode without uninstalling it. Full otherwise activates every registered nonhidden tool, including inactive, deferred and codemode tools. Legacy nonempty subsets retain upstream active-extension carry for display, but execution is limited to the selected builtins; an empty pin remains Chat only.
- The wrapper reasserts this policy after extension binding, `get_tools`, before idle prompts, both reload paths and tree navigation. Successful RPC and extension-command reloads must both restore the local loadout **and** invalidate the shared extension model runtime; neither action replaces the other. `lib/rpc-manager-tool-exposure.test.mjs` checks both immediately after reload, before a later `get_tools` could conceal a missing refresh. Its integration companion tests sanitized bash's SDK registration before binding the wrapper (#1235), then verifies the local plan/build policy after command-context reload. `before_agent_start` also restores policy for runs triggered directly by extensions/custom messages, including pi 1.2's prompt/custom event union. Streaming `get_tools` does not mutate the current run. Chat-only and profile-scoped subagent wrappers are excluded; their resource/extension/MCP policies remain authoritative.
- **SDK restore is underlying behavior, not the local policy.** Since pi 1.3, a normal session created without explicit `tools` restores its transcript's recorded loadout rather than today's `defaultTools`; `navigateTree()` likewise restores the target branch's loadout. Since pi 1.4 (#11062), a newly registered tool that a branch never added or removed defaults active unless registered with `defaultActive: false`. The wrapper sanitizes all these restored/default sets through `localToolPolicy()`: a pin selects its local mode, and no pin (including a cleared pin) always resolves to build, never to an arbitrary recorded loadout. Plan/build never carry arbitrary extension/MCP extras, `codemode` or `tool_search` through restoration or navigation. Full enables all registered nonhidden tools. Chat only (`tools: []`) and profile-scoped subagents (`subagentToolOptions()`: an allowlist, or `noTools: "builtin"`) select tools explicitly and keep their own policies.
- **Allowed set first, stable order second.** `localToolPolicy()` and wrapper navigation resolve the permitted set before `preserveAllowedToolOrder()` considers the previous order. Only an exact, duplicate-free set match keeps that order; otherwise the resolved allowed order wins. This avoids rewriting the prompt's `<tools>` and rules sections and losing the prompt cache on a same-set history edit/navigation (#1405), without allowing an old or restored order to reintroduce forbidden tools.

**Built-in extensions** (`lib/builtin-extensions.ts`, ADR 0006). The CLI's built-in `codemode`, `tool-search` and `mcp` are rebuilt from the factories the SDK root exports, under the CLI's names with `replaceable: true, builtin: true`, so `-builtin:<name>`, project overrides, replacement by a third-party extension and `noExtensions` behave as in the CLI. Normal sessions load all three. Subagents load `codemode` through their profile's `codemode` policy, and `tool-search` and `mcp` with an MCP host of their own only under `mcp: on` (see [subagents.md](subagents.md)); they never share the normal session's.
- The MCP extension's `loadConfig` returns no servers (only `autoEnableCodemode`), so it connects nothing, and with `startupWaitMs: 0`, so its first-prompt wait for `direct` servers (which ignores Stop, and since pi 1.0 also sees servers registered right before the prompt) holds nothing; pi-web registers servers itself (**MCP host** in [mcp-runtime.md](mcp-runtime.md)). Servers connect through `createPiWebMcpTransportFactory()`; `openUrl` opens no browser on the server host.
- MCP is off (the `mcp` entry registers nothing) when `PI_WEB_DISABLE_MCP` is anything but empty, `0` or `false`, or `lib/pi-sdk-internals.ts` cannot load; never fall back to the SDK's own transport.
- `codemode` is offered only after a once-per-process self-test ran a script through the SDK's sandbox (`checkCodemodeSandbox()`). A built-in that cannot run keeps its `builtin:<name>` entry with an empty factory, so a setting naming it means the same.
- pi lets at most two codemode workers live per process, across all sessions (`DEFAULT_MAX_CODEMODE_WORKERS` in the SDK's `dist/extensions/codemode/execute.js`); `PI_CODEMODE_MAX_WORKERS` changes it, read on every script. Since pi 1.4 a script at capacity waits for a free worker in arrival order, up to 60 s or its `timeout_ms`, then fails without running (pi 1.3 failed it at once with "Codemode worker limit reached"). A script holds its worker while it waits on its tool calls. The CLI runs one session per process; pi-web runs every session and subagent in one, so two parent scripts waiting on subagents took both workers and every script those subagents ran timed out. `applyCodemodeWorkerDefault()` (`lib/codemode-workers.ts`, from `instrumentation-node.ts` at server start) therefore sets the variable to 8 when it is unset or empty; any other value the user set is kept, even one pi rejects (it then uses 2). Each worker's QuickJS heap is capped at 256 MB. Eight parent scripts waiting on subagents at once still fill it; only pi releasing a worker while its script waits would end that. `lib/codemode-workers.test.mjs` fails if the SDK stops reading the variable per script.

**Execution policy** (`lib/mcp-read-only-policy.ts` keeps its upstream extension name). Normal sessions use the same `localToolPolicy()` for activation and **every** `tool_call`, including nested/deferred calls, not only MCP calls. Plan/build cannot bypass the builtin allowlist through a loader or script. Plan's trusted `subagent` accepts only scout/planner; build accepts scout/planner/worker/reviewer, including mixed-role parallel batches and chains. The trusted extension forces scout/planner to `read, grep, find, ls` plus optional read-only webfetch in both modes regardless of their profile tools; build worker/reviewer retain their role's builtin tools. Discovered/configured extensions, MCP, skills and templates remain disabled for plan/build children, except the explicitly loaded trusted webfetch. Omitted or `user` agent scope is allowed; any other scope, or any disallowed role in single/tasks/chain, rejects the whole call before any child starts. With the external dispatcher, parent and shared extension policies must be updated and tested together; a parent-only role change cannot enforce the child loadout. With the built-in host enabled, `local-subagent-policy.ts` and `local-subagent-services.ts` enforce the equivalent role/resource ceiling in-process, persist it in the child snapshot and reconstruct it on reopen. Role resolution uses raw global profiles before project shadowing; current-mode checks also gate resume/steering, while reading an owned result is not child execution. Resource discovery uses private in-memory loader settings to avoid configured-package installation side effects; the real session settings are not rewritten. See [subagents.md](subagents.md#fork-planbuild-policy) for continuation, immutable queued/running ceilings and pre-load/reload checks. Stable plan/build/full guidance explicitly describes the **parent's** duties, not only child roles: plan investigates/analyzes/proposes without edits, shell commands or implementation delegation; implementation requires the user-selected build mode. Current declarations and mode take precedence over stale history; chat/steering cannot grant permissions, and models must not probe for missing tools or self-enable them. Build/full explicitly supersede earlier plan-only behavior while retaining tool/profile ceilings. Guidance goes into structured prompt guidelines, or a supported `pi_web_local_mode` custom section for replacement `SYSTEM.md`. Trusted hooks returning an exact forced system prompt remain exact and must compose any mode guidance themselves; execution guards still apply. Final faux-provider and loopback HTTP request tests cover actual declarations/guidance, mode changes, restoration, reload/navigation, replacement/forced prompts and active-run steering. Full permits all registered nonhidden tools. The older MCP read-only-hint guard remains for legacy subsets. Subagents with `mcp: on` keep their separate `createSubagentMcpPolicyExtension()`, reading profile tools rather than the parent mode. Hints and description markers are trusted extension assertions: this prevents model mistakes, not a malicious extension/server.

**`defaultTools` switches.** Code mode's Always on is `+codemode` in the global `defaultTools`; Automatic writes nothing (ADR 0006). `/api/tools/settings` is the only writer of that key, for this and the PowerShell switch, and of the global `codemode.mode` and `codemode.inlineBudget` (Settings › MCP's Built-in tools switch and tool list budget), through `lib/global-settings-file.ts` (the lock pi's `SettingsManager` takes on that file). `lib/codemode-settings.ts` edits only entries naming `codemode` and appends `+codemode`, valid on plain and modifier-only lists; a modifier-only list left empty is removed, since `defaultTools: []` means no tools at all. `defaultTools` may hold `+name` / `-name` modifiers: read it resolved through `SettingsManager.getDefaultTools()`; `lib/powershell-settings.ts` resolves the raw global list by the same rule before editing, since appending a plain name to a modifier-only list drops pi's default tools.
