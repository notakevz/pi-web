# Tool selection and built-in extensions

## New session tool preset
Tool names are passed at session creation (`POST /api/agent/new` → `toolNames[]`) and persisted in versioned `pi-web:tool-selection` custom entries (ADR 0002). No entry, or a later `cleared: true` one, means no pin: ordinary sessions now resolve to local **build** (four coding tools), not pi's `defaultTools`. The legacy `configured` wire sentinel still sends no `toolNames`; no new mode entry format is introduced. An empty array is Chat only, resolved before services are created: no extensions/skills/prompts/themes, and the ordered contents of Pi's discovered context files replace Pi's base prompt. Crossing the Chat-only boundary or clearing a pin rebuilds the wrapper; changing between nonempty presets updates it in place.

**Chat only has no extension providers** (#804): the model selector's listing loads extensions, the session does not. A model only an extension provides (one `findDeferredModel()` remembers but the Chat-only runtime lacks) is named as such: a start refuses it when the browser chose it, `set_model` refuses it instead of "Model not found", and a prompt in a session that could start on no model at all names the one it wanted rather than pi's "No API key found". With no pick, another model in scope stands in for an extension's default, as for any default out of scope.

**Exact system prompts go through `before_agent_start`.** Chat-only sessions register `lib/exact-system-prompt.ts` as an inline extension factory, and subagents (any profile in replace mode, or one naming `skills:`) the equivalent handler in `lib/subagent-skills.ts`, which appends the named skills or, in replace mode, pi's skill catalog; the handler returns `{ systemPrompt }`, which the SDK sends as the provider's leading system prompt for the run while the transcript keeps Pi's structured sections. Assigning `agent.state.systemPrompt` (a getter replayed from transcript system messages) throws, and patching `prepareNextTurnWithContext` never reaches the model. `get_state.systemPrompt` reports the exact prompt for those wrappers. Subagents persist their tools and the profile's skill / extension switches in `resourceSnapshot`, and extensions never expose the reserved `Agent`, `get_subagent_result` or `steer_subagent` to them (ADR 0002).

Every genuinely fresh composer starts in **full** (`NEW_SESSION_TOOL_PRESET`, the complete builtin set `bash, read, edit, write, grep, find, ls`), including after changing folders/remounting. Changing this chat to plan/build is session-scoped and does not change the next fresh composer. The old browser `pi-tool-preset` value is neither read nor rewritten by useAgentSession; `tool-preset-preference.ts` remains only as a legacy compatibility helper. Keep `DEFAULT_TOOL_PRESET` as build for historical unpinned sessions and direct legacy API requests: changing that constant would silently alter existing chats. Existing pinned sessions restore their own `toolNames` from `GET /api/sessions/[id]`, then live `get_tools`; legacy none stays Chat only.

**Tool exposure.** pi activates `direct` and `model-only` tools on registration unless their definition sets `defaultActive: false` (`codemode` and `tool_search` do), leaves `codemode` and `deferred` tools undeclared until something activates them, and ignores `hidden` (withdrawn) tools in `setActiveToolsByName()`; `get_tools` leaves hidden tools out.
- Pi Web's environment-sanitizing `bash` (`lib/project-command-env.ts`, ADR 0001), an extension tool standing in for pi's built-in, sets `defaultActive: false` too, so like the built-in it is on only when `defaultTools` (pi's default list included), a preset or `set_tools` names it; registered active, it came back in every session whatever `defaultTools` left out (#1235). A user extension's `bash` still replaces it (`preferUserBashExtension()`) and activates as in the CLI.
- `get_tools` reports an active tool's description from `agent.state.tools`, what the model is sent. Under `codemode.mode: "only"`, while `codemode` is active, the active `direct` tools stay active and callable (`get_tools` reports them so, with `declarationHidden: true` from the AgentSession's private `_hiddenDeclarations`), but codemode's `hiddenDeclarations` leave their declarations out of every request, so the model reaches them only from scripts. The toolbar's Tools panel lists only what requests declare; presets still read `active`. A preset still bounds them: a `direct` tool is callable only while active. `prepareLoadout` hooks rewrite it there on every loadout change (tool registration included): codemode's definition holds only the intro, while the declared one lists the tools scripts can call, MCP namespaces and types, and appends the codemode declaration to the callable `direct` tools.
- **Fork modes** (`lib/local-tool-modes.ts`): upstream `read-only` / `default` / `full` wire IDs and persisted builtin lists remain plan / build / full respectively. Plan declares `read, grep, find, ls`; build `read, bash, edit, write` (PowerShell follows the existing shell preference). Both admit only two vetted extras, never arbitrary extension/MCP tools: nonhidden `subagent` whose description contains `In plan/build, children cannot load extensions or MCP`, and nonhidden `webfetch` with `readOnlyHint: true` and description containing `Read-only webfetch:`. Full activates every registered nonhidden tool, including inactive, deferred and codemode tools. Legacy nonempty subsets retain upstream active-extension carry for display, but execution is limited to the selected builtins; an empty pin remains Chat only.
- The wrapper reasserts this policy after extension binding, `get_tools`, before idle prompts, both reload paths and tree navigation. Successful RPC and extension-command reloads must both restore the local loadout **and** invalidate the shared extension model runtime; neither action replaces the other. `lib/rpc-manager-tool-exposure.test.mjs` checks both immediately after reload, before a later `get_tools` could conceal a missing refresh. Its integration companion tests sanitized bash's SDK registration before binding the wrapper (#1235), then verifies the local plan/build policy after command-context reload. `before_agent_start` also restores policy for runs triggered directly by extensions/custom messages, including pi 1.2's prompt/custom event union. Streaming `get_tools` does not mutate the current run. Chat-only and profile-scoped subagent wrappers are excluded; their resource/extension/MCP policies remain authoritative.

**Built-in extensions** (`lib/builtin-extensions.ts`, ADR 0006). The CLI's built-in `codemode`, `tool-search` and `mcp` are rebuilt from the factories the SDK root exports, under the CLI's names with `replaceable: true, builtin: true`, so `-builtin:<name>`, project overrides, replacement by a third-party extension and `noExtensions` behave as in the CLI. Normal sessions load all three. Subagents load `codemode` through their profile's `codemode` policy, and `tool-search` and `mcp` with an MCP host of their own only under `mcp: on` (see [subagents.md](subagents.md)); they never share the normal session's.
- The MCP extension's `loadConfig` returns no servers (only `autoEnableCodemode`), so it connects nothing, and with `startupWaitMs: 0`, so its first-prompt wait for `direct` servers (which ignores Stop, and since pi 1.0 also sees servers registered right before the prompt) holds nothing; pi-web registers servers itself (**MCP host** in [mcp-runtime.md](mcp-runtime.md)). Servers connect through `createPiWebMcpTransportFactory()`; `openUrl` opens no browser on the server host.
- MCP is off (the `mcp` entry registers nothing) when `PI_WEB_DISABLE_MCP` is anything but empty, `0` or `false`, or `lib/pi-sdk-internals.ts` cannot load; never fall back to the SDK's own transport.
- `codemode` is offered only after a once-per-process self-test ran a script through the SDK's sandbox (`checkCodemodeSandbox()`). A built-in that cannot run keeps its `builtin:<name>` entry with an empty factory, so a setting naming it means the same.

**Execution policy** (`lib/mcp-read-only-policy.ts` keeps its upstream extension name). Normal sessions use the same `localToolPolicy()` for activation and **every** `tool_call`, including nested/deferred calls, not only MCP calls. Plan/build cannot bypass the builtin allowlist through a loader or script. Plan's trusted `subagent` accepts only scout/planner; build only worker/reviewer. Omitted or `user` agent scope is allowed; any other scope, or any cross-group role in single/tasks/chain, rejects the whole call before any child starts. Mode guidance is appended to structured prompt guidelines. Full permits all registered nonhidden tools. The older MCP read-only-hint guard remains for legacy subsets. Subagents with `mcp: on` keep their separate `createSubagentMcpPolicyExtension()`, reading profile tools rather than the parent mode. Hints and description markers are trusted extension assertions: this prevents model mistakes, not a malicious extension/server.

**`defaultTools` switches.** Code mode's Always on is `+codemode` in the global `defaultTools`; Automatic writes nothing (ADR 0006). `/api/tools/settings` is the only writer of that key, for this and the PowerShell switch, and of the global `codemode.mode` and `codemode.inlineBudget` (Settings › MCP's Built-in tools switch and tool list budget), through `lib/global-settings-file.ts` (the lock pi's `SettingsManager` takes on that file). `lib/codemode-settings.ts` edits only entries naming `codemode` and appends `+codemode`, valid on plain and modifier-only lists; a modifier-only list left empty is removed, since `defaultTools: []` means no tools at all. `defaultTools` may hold `+name` / `-name` modifiers: read it resolved through `SettingsManager.getDefaultTools()`; `lib/powershell-settings.ts` resolves the raw global list by the same rule before editing, since appending a plain name to a modifier-only list drops pi's default tools.
